# Specyfikacja Warstwy Semantycznej (AST), Obsługi Miar Nieaddytywnych i Telemetrii

## 1. Problem Miar Nieaddytywnych (Średnie Ważone i Wskaźniki Proporcjonalne)
W hurtowniach danych miary dzielimy na:
1. **Miary bazowe (Addytywne):** Takie, które można bezpiecznie sumować między kolejnymi dniami i wymiarami (np. `SUM(revenue)`, `SUM(cost)`, `COUNT(trips)`).
2. **Miary pochodne (Nieaddytywne / Wskaźniki proporcjonalne):** Wyrażone wzorami matematycznymi zależnymi od innych kolumn, np.:
   * $\text{ROI} = \left(\frac{\text{Net Return}}{\text{Cost of Investment}}\right) \times 100$
   * $\text{Tip Ratio (\%)} = \left(\frac{\text{Total Tips}}{\text{Base Fare}}\right) \times 100$
   * $\text{Średnia prędkość (mph)} = \frac{\sum \text{Dystans}}{\sum \text{Czas trwania}}$

### Złota zasada architektury (Rozwiązanie problemu "średniej ze średnich"):
Lokalne pliki Parquet (zmaterializowane dzienne paczki dla DuckDB) **NIGDY nie przechowują wyliczonych miar pochodnych ani średnich**. Przechowują wyłącznie dzienne zsumowane miary bazowe (liczniki i mianowniki).

Gdy użytkownik pyta o okno np. **23 dni**:
1. Parser formuł (moduł `ast` Pythona -> AST domenowe, ADR-009) odczytuje wzór z pliku YAML, np. `tip_to_fare_ratio_pct: "(total_tip_amount / total_fare_amount) * 100"`.
2. Rozwija drzewo zależności (DAG) do miar bazowych. Postać liścia zależy od silnika (dok. 03, Moduł 1):
   * BigQuery (surowa tabela): `total_tip_amount` -> `SUM(tip_amount)`, `total_fare_amount` -> `SUM(fare_amount)`.
   * DuckDB (rollup Parquet): `total_tip_amount` -> `SUM(total_tip_amount)`, `total_fare_amount` -> `SUM(total_fare_amount)` (suma dziennych sum).
3. Zabezpiecza każde dzielenie przed dzieleniem przez zero, opakowując mianownik w funkcję `NULLIF(mianownik, 0)` (wyjątek: mianownik będący niezerową stałą liczbową, np. `/ 3600.0`).
4. Generuje zapytanie SQL (dla DuckDB lub BigQuery), które **najpierw sumuje miary bazowe z 23 dni**, a dopiero na samym końcu wykonuje dzielenie i mnożenie (przykład dla DuckDB):
   ```sql
   SELECT
     vendor_id,
     (SUM(total_tip_amount) / NULLIF(SUM(total_fare_amount), 0)) * 100 AS tip_to_fare_ratio_pct
   FROM read_parquet('./data/nyc_taxi/pickup_date=*/rollup.parquet', hive_partitioning = true)
   WHERE pickup_date BETWEEN CAST('2022-12-01' AS DATE) AND CAST('2022-12-23' AS DATE)
   GROUP BY vendor_id
   ```

## 2. Flagi Badawcze i Sterowanie Wykonaniem (Benchmarking Mode)
Aby umożliwić przeprowadzenie rzetelnych eksperymentów do pracy magisterskiej, każde zapytanie do API przyjmuje opcjonalny obiekt sterujący `control` (pełny kontrakt: dok. 03, sekcja 4):

* `execution_mode`:
  * `"auto"` (Domyślny): Router sam analizuje AST (zakres dat, dostępność wymiarów w rollupie, fizyczna obecność partycji Parquet) i wybiera DuckDB lub BigQuery.
  * `"force_duckdb"`: Wymusza wykonanie na lokalnych plikach Parquet. Jeśli w zapytaniu (w `dimensions`, `filters` lub `order_by`) użyto wymiaru o wysokiej ziarnistości, nieobecnego w rollupie (`in_rollup: false`, np. `dropoff_location_id`), system natychmiast zwraca błąd `GranularityNotSupportedInLocalCacheError` (HTTP 400). Jeśli brakuje partycji dla któregokolwiek dnia zakresu -> `CacheMissInForcedModeError` (HTTP 400). Jeśli zapytanie używa miary holistycznej (np. `COUNT_DISTINCT`, ADR-011) -> `NonAdditiveMeasureInLocalCacheError` (HTTP 400).
  * `"force_bigquery"`: Wymusza pominięcie lokalnego cache'u i wysłanie zapytania bezpośrednio do surowej tabeli w Google BigQuery (używane do budowania tabeli porównawczej w pracy magisterskiej).
* `include_telemetry`: `bool` (Domyślnie `false` na produkcji, `true` podczas badań).
  * Gdy `false`: System nie zbiera rozszerzonych statystyk i zwraca wyłącznie surowe dane (`data`), eliminując jakikolwiek narzut pomiarowy.
  * Gdy `true`: Zwraca bogaty obiekt `telemetry` zawierający: wybrany silnik, powód decyzji routera, wygenerowany tekst zapytania SQL, czas kompilacji AST (ms), czas wykonania w silniku (ms), ilość przeskanowanych bajtów (dla BQ z `dry_run` oraz po wykonaniu) i szacowany koszt w USD.
* `confirm_high_cost`: `bool` (Domyślnie `false`) – potwierdzenie wykonania zapytania przekraczającego limity Cost Guard.
  * Limity i tryb działania definiuje sekcja `cost_guard` w YAML modelu: `max_bytes_per_query` (10 GB), `max_cost_usd_per_query`, `price_per_tb_usd` oraz `action_on_exceed`.
  * `action_on_exceed: "raise_error"` -> `CostTooHighForQueryException` (HTTP 403); `confirm_high_cost` jest ignorowane.
  * `action_on_exceed: "require_confirmation"` -> HTTP 409 z `status: "confirmation_required"`, przeskanowanymi bajtami i kosztem w USD z `dry_run`; zapytanie należy ponowić z `confirm_high_cost: true`.
  * `action_on_exceed: "silent_allow"` (tryb produkcyjny) -> zapytanie wykonuje się mimo przekroczenia limitu; `confirm_high_cost` jest ignorowane; przekroczenie jest logowane (ostrzeżenie), a koszt z `dry_run` trafia do telemetrii.
