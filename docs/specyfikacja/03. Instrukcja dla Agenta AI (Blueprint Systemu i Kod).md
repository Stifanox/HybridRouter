## 2\. Specyfikacja Pliku Konfiguracyjnego YAML (`configs/nyc_taxi.yaml`)

System jest w 100% *data-agnostic*. Cała wiedza o zbiorze danych pochodzi z pliku YAML. Wyrażenia w `derived_metrics` są definiowane jako czytelne stringi matematyczne (Opcja 1), które parser zamienia na AST.

```
model_name: "nyc_yellow_taxi_analytics"
description: "Model analityczny przejazdów taksówek w Nowym Jorku (BigQuery Public Dataset)"

storage:
  bigquery:
    project_id: "twoj-projekt-gcp"
    dataset_table: "bigquery-public-data.new_york_taxi_trips.tlc_yellow_trips_2022"
    timestamp_column: "pickup_datetime"
    partition_granularity: "DAY"
    use_query_cache: false # false = uczciwe pomiary latencji/kosztu (benchmarki)
  local_cache:
    base_path: "./data/nyc_taxi"
    file_format: "parquet"
    partition_scheme: "hive" # data/nyc_taxi/pickup_date=YYYY-MM-DD/rollup.parquet
    partition_key: "pickup_date" # musi być nazwą wymiaru typu date z in_rollup: true
    # Domyślny zakres materializacji dla SyncWorkera (gdy nie podano --start-date/--end-date).
    # NIE jest źródłem prawdy dla routera – ten sprawdza fizyczną obecność partycji (Moduł 2).
    date_window_start: "2022-10-01"
    date_window_end: "2022-12-31"

cost_guard:
  enabled: true
  price_per_tb_usd: 6.25
  max_bytes_per_query: 10737418240 # 10 GiB twardy limit
  max_cost_usd_per_query: 0.0625
  action_on_exceed: "require_confirmation" # "raise_error" (HTTP 403), "require_confirmation" (HTTP 409) lub "silent_allow" (wykonaj mimo przekroczenia)

# Wymiary (Dimensions) - flaga in_rollup określa, czy wymiar jest zapisywany w lokalnym Parquet
dimensions:
  pickup_date:
    sql: "DATE(pickup_datetime)"
    type: "date"
    in_rollup: true
  vendor_id:
    sql: "CAST(vendor_id AS STRING)"
    type: "string"
    in_rollup: true
  payment_type:
    sql: "CAST(payment_type AS STRING)"
    type: "string"
    in_rollup: true
  rate_code:
    sql: "CAST(rate_code AS STRING)"
    type: "string"
    in_rollup: true
  # Wymiar szczegółowy (Wysoka kardynalność) - NIEOBECNY w lokalnym rollupie DuckDB!
  # Zapytanie o ten wymiar w trybie 'auto' wymusi fallback do BigQuery.
  dropoff_location_id:
    sql: "CAST(dropoff_location_id AS STRING)"
    type: "string"
    in_rollup: false

# Miary Bazowe (Base Measures). Dozwolone aggregation – rejestr AGGREGATIONS (ADR-010):
#   SUM, COUNT, MIN, MAX  – rozdzielne, materializowane w Parquet;
#   COUNT_DISTINCT        – holistyczna, NIE trafia do rollupu, zapytania z nią idą do BigQuery (ADR-011);
#   AVG                   – zabronione (zdefiniuj jako metrykę pochodną SUM/COUNT).
base_measures:
  trips_count:
    aggregation: "COUNT"
    sql: "1"
  total_fare_amount:
    aggregation: "SUM"
    sql: "fare_amount"
  total_tip_amount:
    aggregation: "SUM"
    sql: "tip_amount"
  total_revenue:
    aggregation: "SUM"
    sql: "total_amount"
  total_distance_miles:
    aggregation: "SUM"
    sql: "trip_distance"
  total_passenger_count:
    aggregation: "SUM"
    sql: "passenger_count"
  total_duration_seconds:
    aggregation: "SUM"
    sql: "TIMESTAMP_DIFF(dropoff_datetime, pickup_datetime, SECOND)"
  # Miara holistyczna (przypadek badawczy ADR-011) – nazwa kolumny do weryfikacji dry_run
  unique_pickup_zones:
    aggregation: "COUNT_DISTINCT"
    sql: "pickup_location_id"

# Miary Pochodne (Derived Metrics - Nieaddytywne, wyliczane w locie po zgrupowaniu!)
derived_metrics:
  # Wskaźnik proporcjonalny (odpowiednik ROI)
  tip_to_fare_ratio_pct:
    formula: "(total_tip_amount / total_fare_amount) * 100"
    description: "Stosunek napiwków do kwoty bazowej przejazdu w procentach"
  
  # Wielopoziomowa metryka pochodna (odwołuje się do miar bazowych)
  non_fare_surcharges:
    formula: "total_revenue - total_fare_amount - total_tip_amount"
    description: "Suma podatków, opłat drogowych i dopłat"

  surcharge_to_revenue_roi_pct:
    formula: "(non_fare_surcharges / total_revenue) * 100"
    description: "Udział opłat dodatkowych w całkowitym przychodzie (%)"

  # Średnie ważone (nigdy nie uśredniamy średnich!)
  avg_revenue_per_mile:
    formula: "total_revenue / total_distance_miles"
    description: "Średni przychód na jedną przejechaną milę ($/mile)"

  avg_trip_speed_mph:
    formula: "total_distance_miles / (total_duration_seconds / 3600.0)"
    description: "Rzeczywista średnia ważona prędkość przejazdów w milach na godzinę"

  # Funkcja skalarna z rejestru SCALAR_FUNCTIONS (ADR-010)
  avg_fare_per_trip:
    formula: "ROUND(total_fare_amount / trips_count, 2)"
    description: "Średnia opłata bazowa na przejazd (zaokrąglona do centów)"

```

## 3\. Szczegółowe Wymagania Implementacyjne dla Modułów (Dla Agenta AI)

### Moduł 1: AST domenowe, Parser Wzorów, Plan Logiczny i Renderery (`app/semantic/`, `app/planner/`, `app/renderers/`)

Potok kompilacji (ADR-008): formuła YAML -> AST domenowe -> plan logiczny -> routing -> AST `sqlglot` -> SQL w dialekcie silnika.

1. **AST domenowe (`ast_nodes.py`, ADR-009):** niemutowalne dataclassy `MeasureRef(name)`, `Literal(value)`, `BinaryOp(op, left, right)`, `UnaryOp(op, operand)`, `FunctionCall(name, args)` oraz bazowy `Visitor`. AST nie importuje `sqlglot`.
2. **Parser formuł (`formula_parser.py`):** `ast.parse(formula, mode="eval")` + konwersja na AST domenowe z **białą listą**: `BinOp` (`Add`, `Sub`, `Mult`, `Div`), `UnaryOp` (`USub`), `Constant` (int/float), `Name` (nazwa miary bazowej lub metryki pochodnej), `Call` (tylko funkcje z `SCALAR_FUNCTIONS`, z kontrolą liczby argumentów). Każdy inny węzeł -> `FormulaSyntaxError` z nazwą metryki i pozycją.
3. **Rejestry (`registry.py`, ADR-010):** `AGGREGATIONS` (`SUM->SUM`, `COUNT->SUM`, `MIN->MIN`, `MAX->MAX`, `COUNT_DISTINCT->None`) oraz `SCALAR_FUNCTIONS` (`ROUND`, `COALESCE`, `ABS`, `GREATEST`, `LEAST`). Agregacje nie mogą występować w formułach.
4. **Rozwijanie zależności (`resolver.py`):** jeśli metryka pochodna A odwołuje się do metryki pochodnej B (jak `surcharge_to_revenue_roi_pct` -> `non_fare_surcharges`), rekurencyjnie podstaw AST B, aż wszystkie liście `MeasureRef` wskazują `base_measures`. Wykryj cykle (`CircularDependencyError` ze ścieżką cyklu) i nieznane nazwy (`UnknownMeasureError`). Wynik jest cache'owany per model.
5. **Plan logiczny (`planner/`):** `LogicalQuery` zawiera: wymiary (definicje z YAML), metryki (nazwa + rozwinięte AST), filtry (wymiar, operator, wartości), sortowanie, limit, wyliczony zakres dat (z filtrów na `partition_key`) oraz zbiór użytych miar bazowych (dla Warunku 3 routera).
6. **Renderery (`renderers/`):** zamieniają plan na AST `sqlglot`. Renderer zależy od **typu źródła**, dialekt jest osobnym parametrem `render(plan, dialect)`:
  * **`RawTableRenderer`** (surowa tabela – BigQuery lub surowe dane testowe): liść `total_fare_amount` -> `SUM(fare_amount)` (funkcja z `aggregation`, wyrażenie z `sql`); wymiar -> wyrażenie z pola `sql` aliasowane nazwą wymiaru (np. `CAST(vendor_id AS STRING) AS vendor_id`).
  * **`RollupRenderer`** (dzienny rollup Parquet): liść -> funkcja re-agregacji z rejestru na kolumnie rollupu, np. `SUM(total_fare_amount)`, `SUM(trips_count)` (COUNT -> SUM); wymiar -> sama nazwa kolumny (`vendor_id`, `pickup_date`). Miara z `rollup_reaggregate = None` -> błąd (nie powinna tu trafić – chroni Warunek 3 routera).
  * Fragmenty `sql` z YAML są w dialekcie BigQuery: parsuj je `sqlglot.parse_one(fragment, read="bigquery")`. To jedyne miejsce transpilacji międzydialektowej.
  * Reguła dotyczy `SELECT`, `WHERE`, `GROUP BY` i `ORDER BY`.
7. **Zabezpieczenie dzielenia (NULLIF Guard, w rendererze):** każdy węzeł `BinaryOp("/", A, B)` jest renderowany jako `A / NULLIF(B, 0)`. Wyjątek: gdy `B` jest niezerowym `Literal` (np. `/ 3600.0`), węzeł pozostaje bez zmian.
5. **Operatory filtrów:** API przyjmuje `==`, `!=`, `>`, `>=`, `<`, `<=`, `in`, `not_in`; kompilator mapuje je na SQL odpowiednio `=`, `<>`, `>`, `>=`, `<`, `<=`, `IN`, `NOT IN`. Filtry mogą dotyczyć wyłącznie wymiarów (filtrowanie po metrykach / `HAVING` jest poza zakresem). Wartości są wstawiane jako literały AST sqlglot (nigdy przez konkatenację stringów – ochrona przed SQL injection).

### Moduł 2: Silnik Decyzyjny Routera (`app/router/decision_engine.py`)

Wejście: Zwalidowany obiekt `QueryRequest` oraz `ModelConfig`.

**Indeks dostępnych partycji:** router utrzymuje w pamięci zbiór dat, dla których istnieje plik `{base_path}/pickup_date=YYYY-MM-DD/rollup.parquet` (pliki `.tmp` są ignorowane). Indeks jest budowany przy starcie aplikacji i odświeżany po każdym przebiegu SyncWorkera (oraz okresowo, np. co 60 s). Oba tryby (`auto` i `force_duckdb`) korzystają z tego samego sprawdzenia „Warunek 2” poniżej.

**Zakres dat zapytania** wyznacza się z filtrów na wymiarze `partition_key` (`>=`, `>`, `<=`, `<`, `==`, `in`). Jeśli zakres nie jest ograniczony z obu stron (brak filtra daty lub tylko jedna granica), zapytanie traktuje się jako niepokryte przez cache.

Algorytm wyboru silnika:

* Warunek 1 (Ziarnistość): Czy wszystkie wymiary użyte w `dimensions`, `filters` i `order_by` mają `in_rollup == True`?
* Warunek 2 (Pokrycie czasowe): Czy zakres dat jest ograniczony i **każdy** dzień zakresu ma partycję w indeksie?
* Warunek 3 (Addytywność, ADR-011): Czy wszystkie miary bazowe użyte w planie (po rozwinięciu metryk pochodnych) mają w rejestrze funkcję re-agregacji (`rollup_reaggregate is not None`)?

1. Jeśli `execution_mode == "force_bigquery"` -> zwróć `BIGQUERY`.
2. Jeśli `execution_mode == "force_duckdb"`:
  * Warunek 1 niespełniony -> rzuć `GranularityNotSupportedInLocalCacheError` (HTTP 400).
  * Warunek 2 niespełniony -> rzuć `CacheMissInForcedModeError` (HTTP 400, z listą brakujących dni).
  * Warunek 3 niespełniony -> rzuć `NonAdditiveMeasureInLocalCacheError` (HTTP 400, z nazwą miary).
  * W przeciwnym razie -> zwróć `DUCKDB`.
3. Jeśli `execution_mode == "auto"`:
  * Jeśli Warunki 1, 2 i 3 są spełnione -> zwróć `DUCKDB`.
  * Jeśli którykolwiek warunek nie jest spełniony -> wykonaj **Full Fallback** i zwróć `BIGQUERY` (wraz z zapisaniem powodu fallbacku do telemetrii, np. `"reason": "Dimension 'dropoff_location_id' not present in local rollup"`).

### Moduł 3: Wykonawca BigQuery i Cost Guard (`app/executors/bigquery_executor.py`)

1. Przed właściwym wykonaniem zapytania utwórz `QueryJobConfig(dry_run=True, use_query_cache=False)`.
2. Wyślij zapytanie Dry-Run do API BigQuery i odczytaj `job.total_bytes_processed`.
3. Wylicz szacowany koszt: `estimated_cost_usd = (bytes_processed / (1024**4)) * config.cost_guard.price_per_tb_usd`.
4. Limit jest przekroczony, gdy `bytes_processed > max_bytes_per_query` **lub** `estimated_cost_usd > max_cost_usd_per_query` (gdy `cost_guard.enabled == False`, krok jest pomijany):
  * `action_on_exceed == "raise_error"` -> rzuć `CostTooHighForQueryException(bytes_processed, estimated_cost_usd, generated_sql)` -> HTTP 403. Flaga `confirm_high_cost` jest ignorowana.
  * `action_on_exceed == "require_confirmation"` i `confirm_high_cost == False` -> rzuć `CostConfirmationRequiredException(bytes_processed, estimated_cost_usd, generated_sql)` -> HTTP 409, body `{"status": "confirmation_required", "bytes_processed": ..., "estimated_cost_usd": ..., "compiled_sql": ...}`.
  * `action_on_exceed == "require_confirmation"` i `confirm_high_cost == True` -> kontynuuj.
  * `action_on_exceed == "silent_allow"` (tryb produkcyjny) -> kontynuuj bez błędu i bez potwierdzenia (`confirm_high_cost` ignorowana); zaloguj ostrzeżenie z `bytes_processed` i `estimated_cost_usd` (wartości trafiają też do telemetrii).
5. Wykonaj właściwe zapytanie z `QueryJobConfig(use_query_cache=config.storage.bigquery.use_query_cache, maximum_bytes_billed=...)`. `maximum_bytes_billed` = `max_bytes_per_query`, a przy dopuszczonym przekroczeniu (`require_confirmation` + `confirm_high_cost == True` lub `silent_allow`) = `bytes_processed` z dry-run powiększone o margines 10%.

### Moduł 4: Wykonawca DuckDB (`app/executors/duckdb_executor.py`)

1. Zaimplementuj pulę/singleton połączenia `duckdb.connect(database=':memory:')`.
2. Dla każdego żądania HTTP twórz odizolowany kursor: `cursor = main_con.cursor()`.
3. Kompiluj klauzulę `FROM` do postaci wykorzystującej partycjonowanie Hive: `FROM read_parquet('./data/nyc_taxi/pickup_date=*/rollup.parquet', hive_partitioning = true)` (wzorzec jawnie wskazuje `rollup.parquet`, więc pliki `.tmp` nigdy nie są czytane).
4. SQL generuj z `RollupRenderer`: `expression.sql(dialect="duckdb")`. Nie transpiluj tekstu SQL (ADR-008).

### Moduł 5: Synchronizator i Atomowy Zapis (`app/sync/`)

1. Skrypt CLI przyjmujący parametry: `--config configs/nyc_taxi.yaml --start-date 2022-12-01 --end-date 2022-12-31` (bez dat -> `local_cache.date_window_start` .. `date_window_end`).
2. Na podstawie sekcji `dimensions` (tylko te z `in_rollup: true`, wyrażenia z pola `sql` aliasowane nazwą wymiaru) oraz `base_measures` z funkcją re-agregacji (oryginalna funkcja agregacji, alias = nazwa miary; miary holistyczne są pomijane) w pliku YAML, skrypt automatycznie generuje zapytanie SQL `GROUP BY` dla BigQuery. Zapytanie przechodzi przez Cost Guard (Moduł 3). Generator (`app/sync/rollup_query.py`) jest wspólny dla SyncWorkera i lokalnego budowania rollupów w testach (ADR-012).
3. Pobiera wyniki (najlepiej przez `BigQuery Storage Read API` do tabeli `PyArrow`) i dzieli je po kolumnie `pickup_date`.
4. Dla każdego dnia zapisuje plik na dysku używając wzorca **Atomic Write**:

```
target_dir = Path(f"{base_path}/pickup_date={date_str}")
target_dir.mkdir(parents=True, exist_ok=True)
tmp_file = target_dir / "rollup.parquet.tmp"
final_file = target_dir / "rollup.parquet"
pq.write_table(arrow_table_for_day, tmp_file, compression="snappy")
os.replace(tmp_file, final_file) # Operacja atomowa na poziomie systemu plików OS

```

5. Po zakończeniu synchronizacji wywołaj odświeżenie indeksu dostępnych partycji routera (Moduł 2). Kolumna `pickup_date` nie jest zapisywana wewnątrz pliku Parquet – pochodzi z nazwy katalogu (Hive).

## 4\. Kontrakt API (JSON Request & Response)

### Przykładowy Request (`POST /api/v1/query`)

```
{
  "model": "nyc_yellow_taxi_analytics",
  "dimensions": ["pickup_date", "vendor_id"],
  "metrics": ["trips_count", "total_revenue", "tip_to_fare_ratio_pct", "avg_trip_speed_mph"],
  "filters": [
    {"field": "pickup_date", "op": ">=", "value": "2022-12-01"},
    {"field": "pickup_date", "op": "<=", "value": "2022-12-23"},
    {"field": "payment_type", "op": "==", "value": "1"}
  ],
  "order_by": [
    {"field": "pickup_date", "direction": "ASC"}
  ],
  "limit": 1000,
  "control": {
    "execution_mode": "auto",
    "include_telemetry": true,
    "confirm_high_cost": false
  }
}

```
